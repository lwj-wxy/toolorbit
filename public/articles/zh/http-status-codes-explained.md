## HTTP 状态码：接口应该怎么表达结果

浏览器、前端应用和后端服务都会根据 HTTP 状态码判断请求结果。状态码不是装饰字段，它会影响缓存、重试、监控、报警和客户端错误处理。

### 1. 常见分类
* **2xx：请求成功。** `200 OK` 表示请求已成功处理。创建资源时，`201 Created` 更清楚。
* **3xx：需要跳转。** `301` 表示永久重定向，`302` 表示临时重定向。它们会影响浏览器缓存和搜索引擎处理。
* **4xx：客户端请求有问题。** `400 Bad Request` 常用于请求格式错误。`401 Unauthorized` 表示未认证，`403 Forbidden` 表示已认证但没有权限。`404 Not Found` 表示资源不存在。
* **5xx：服务端处理失败。** `500 Internal Server Error` 表示服务端内部错误。`502 Bad Gateway` 常见于网关或反向代理无法从上游服务拿到有效响应。

### 2. 不要把所有失败都包装成 200
一个常见反模式是：后端捕获所有异常，然后始终返回 `200 OK`，只在 JSON 里写 `{"success": false, "error": "报错了"}`。

这样做会带来几个问题：

* CDN 和浏览器无法根据状态码判断缓存策略。
* 监控系统看不到真实错误率。
* 客户端必须解析业务字段才能知道请求是否失败。
* 重试、降级和告警规则会变复杂。

如果用户未登录，就返回 `401`。如果没有权限，就返回 `403`。如果服务端异常，就返回 `500` 或更具体的 5xx。业务错误可以放在响应体里，但状态码也要表达同一件事。

### 总结
状态码要反映请求结果。前端、网关、监控和第三方调用方都依赖它做判断。把错误藏进 `200` 响应体里，只会把简单问题推给下游。
